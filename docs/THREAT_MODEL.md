# Threat model

Last reviewed: 2026-10-03; the Apply for me sensitive-answers store row was added 2026-09-30, the Apply agent (Finish in browser) row 2026-10-03, and the Apply agent on Lever (résumé) row 2026-10-08. Scope: API, browser UI, extension, worker, SQLite/PostgreSQL data, private files, and sandbox provider adapters.

| Asset / boundary | Primary threats | Implemented control | Verification |
|---|---|---|---|
| Student, employer, admin APIs | tenant/role confusion, token theft | distinct constant-time bearer checks; strict session cookie; ownership predicates | role-isolation tests |
| Browser session | CSRF, XSS, clickjacking | SameSite cookie, double-submit CSRF on browser writes, CSP, no inline script, frame denial | security middleware tests |
| Resume/capture upload | malware, polyglots, decompression abuse | allowlisted signatures/types, bounded reads, deterministic scan, private generated filenames | hostile upload tests |
| Posting/email/employer text | prompt/tool injection | untrusted text is evidence only; deterministic tool router; consequential proposal approval | hostile content tests |
| Dossier/candidate handoff | over-sharing, stale access | item-level preview, hashed expiring grant, revocation checked on every read, access log | consent/revocation tests |
| Extension | over-broad access, accidental submit | activeTab permission, sensitive-field review, no submit implementation or DOM action | source/static fixtures |
| Apply for me sensitive-answers store | an answer given without the student's consent or for another use; a stored answer read by employer views, reports or the extension; demographic data collected; a local script adding, reading or removing entries; one employer's notice taken as another's; a changed statement or document agreed to unseen | entries are added only by the student, with an unticked-by-default consent recording its time and scope, and used only to fill application forms; EEO questions are stored only as a decline answer, checked in the service, so the table holds no demographic value and "Demographic attributes are deliberately not collected" stays true; export control, citizenship, clearance, salary and every uncategorized question are refused; matching is exact (question, category, company), a statement is stored word for word, and one that reads or links a document, or leans on a description, is saved for one company with the form's own addresses shown and compared with the stored ones, and a question that depends on its company is never kept for any company; a broad wording net (spec 7.3) keeps any possibly sensitive question at its own company, leaves criminal, personal-detail, pay and security questions to the student, and never lets an agreement box be ticked from the answer library; a question is stored only under the kind the classifier reads it as, so a demographic question cannot be filed as work authorization; the store is read only by the apply plan, never by `apply_context`, `/api/v1/extension/*`, the answer library, employer or report code; its routes need the student's browser session with CSRF, so a request that sends the access token in `.env` as an Authorization header is refused (a guard against a stray script: the token can still sign in a browser session, and the account export includes the stored answers, spec 5.7) | `tests/test_apply_sensitive.py`, `tests/test_apply_api.py` (browser-session, refusal and no-leak tests), the store-reader source scan |
| Apply agent (Finish in browser) | a wrong answer sent as the student's own; a duplicate; a request that could carry the application before the student's press; a submission recorded but never sent, or sent but not recorded; a window left open or a second press after a stop; a page script reading typed answers; Greenhouse's telemetry carrying an answer; the emailed security code misused or logged; a typed code that submits by itself; a file uploaded unseen; screenshots exposed; the claim left open when the window is gone | exact sources only, the company rule and the plan preview (spec 7.1); the application and job locks, tombstones and the limits counted from hand-overs; the agent never presses Submit (the student does, spec D1 B): before the press every non-GET except the CAPTCHA service's own requests is refused, and the press goes through only after the app has recorded the attempt (the hand-over commits inside the route handler before the POST continues, a refused or late hand-over aborts it); after the hand-over nothing is called unsent except from the route's own record, and the window is confirmed closed by process id before anything is called unsent; Stop, a closed window and the 20 minute limit close the window first; a second press, an upload, or a send to an address the app does not recognize is stopped; Greenhouse's telemetry hosts are refused outright and the value guard checks plain, URL-encoded and base64 forms of every value the app planned, in every request except the submit POST itself and, after the press, reads from Greenhouse's own board addresses (an answer the student types in the window is not known to the app, so it is not guarded: known-defects); the security code is read from Gmail read-only, from a verified Greenhouse sender, after the hand-over, for the same company, typed once into the same window, never stored or logged (the picture taken at the end covers the code boxes), and the route refuses any submit POST while it is typed and for two seconds after, so a widget that sends on the last character sends nothing and the student presses Submit; a widget that waits longer is not stopped (known-defects); once typed, the employer's page scripts can read answers (including sensitive ones), so the app's control is the request guard, not secrecy from the page (spec 11); consent boxes are ticked only from an exact stored statement and listed before the press; only the latest approved cover letter for the role is attached, to the required field named cover_letter, after a last check that it is still the latest approved version with the same text and the file name the preview shows; otherwise it is left for the student; screenshots live under `data/private/apply/`, masked per field (sensitive questions, and the questions the app never answers that the student types in the window), readable only in the student's own signed-in browser, kept 90 days; the claim is settled by every exit of the runner and by recovery after a crash; pausing automation does not stop a window the student opened (their own Submit is the confirm) and the pause reply says so; the tracker never moves by itself: the card asks "Mark as applied?" | `tests/test_apply_handoff.py`, `tests/test_apply_agent_browser.py` (handoff), `tests/test_apply_security_code.py`, `tests/test_apply_runner.py`, `tests/ui/test_apply_handoff.py` |
| Apply agent on Lever (the résumé sent when it is attached) | the student's résumé reaching a third party unseen, unrecorded or unasked; a file other than the confirmed one, a second one or another kind of upload reaching Lever; Lever's résumé reader leaving a guess in the form as if it were the student's fact; a run described as "nothing was sent" after Lever already holds the file; the student's own attach in the window changing fields unseen | Built here: Lever's page reads a résumé the moment it is attached (spec 3.8), so attaching is itself a send, and the app does it only behind its own setting, `apply_lever_resume_upload`, off by default and never turned on by an agent (it needs `apply_agent_lever`); the start says in plain words, before the window opens, that the file goes to Lever before the student presses Submit, or that it is left for the student, and reads the check again when the student presses the button, so a setting changed in another tab shows its new words and starts nothing; a run the app will attach the file for is marked `resume_attach_planned` when it starts, and the window records `resume_sent_to_lever` when it is ready, so a run that dies in between reads "Your application was not sent. Lever may have received your résumé."; a run that ends before Submit once the file is with Lever reads "Your application was not sent. Lever received your résumé.", never "Nothing was sent" alone, including a stopped claim that recovery settles; the page shows the record and the Stop help does not promise that nothing is sent. Lands with the Lever adapter, not built yet: the request guard that lets exactly one request through for the app's attach, `POST {origin}/parseResume` on the posting's own Lever host, once, with the planned file's bytes, and no other upload, no other non-GET and no telemetry host (spec 7); clearing a field the reader filled where the app has no confirmed fact, with a read-back (L2 A); naming the fields Lever changed after the student's own attach in the window, never their values; never touching a hCaptcha or pressing Lever's Submit button | `tests/test_apply_lever_resume_words.py`, `tests/test_apply_lever_resume_run.py`, `tests/test_apply_lever_check.py`, `tests/ui/test_apply_lever_handoff.py`; the request-policy and browser tests of the adapter (spec 10.2, 10.4 items 1 to 5 and 11) are still to be written |
| Providers/notifications | credential disclosure, unwanted delivery | token-at-rest adapter, disconnect erasure, sandbox-suppressed development outbox, opt-outs | lifecycle tests |
| Operations | replay, overload, silent job loss | idempotency keys, per-client rate limits, durable retries/dead letters, lease recovery, queue backpressure signal | operations tests |
| Backups | plaintext exposure, unusable restore | Fernet encryption, integrity check, documented restore drill | backup/restore test |

Residual risks: local bearer tokens remain appropriate only for the current-user/invited-tester deployment. Public signup requires a managed identity provider, per-user identities, external penetration testing, and live-provider compliance review. Demographic attributes are deliberately not collected, so subgroup error rates are reported as not measurable rather than fabricated.
